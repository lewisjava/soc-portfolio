# Log analysis with SIEM
SIEMS are used to analyse and correlate logs to quickly id malicious activity and compromised activity. Effective use of a SIEM is a core SOC analysts skill.

SIEMS offer many benefits including:

- Centralisation: Instead of having to check logs in different places like network devices, cloud services, identity providers, etc... SIEMS gathers all the data in one place.

- Correlation: SIEMs allow the ability to link seperate events and piece them together to form a complete picture of an event. For example the SIEM alerts to internal network discovery activity which just provides an IP but with sysmon and window event logs this IP and IDS alert can be enriched to build context

- Historical events: SIEM also allows looking at past events. this helps to spot patterns or threats that may have started earlier but weren't noticed at the time.

SIEMs have many types of different log sources:

1. Host-based log sources: These are logs from individual devices within an org. Thi includes workstations, servers etc. A lot of data comes from these devices since nearly every attack involves a host in some way.
    - Authentication logs
    - Account management
    - Process auditing
    - Object access
    - Policy changs
    - Sytem events

2. Network-based logs sources: These are logs collected from network devices such as firewalls, routers, IDS and IPS and other systems
    - Firewall logs
    - IDS/IPS logs
    - Router logs
    - VPN logs
    - Proxy server logs
    - DNS logs

3. Web-based log sources: Almost every org has its own web application and logs from it are also sent to the SIEM. It is through web vulnerabilities that attackers often gain access to an orgs environment, so careful monitoring of web events is an essential part of every analysts's role in a SOC environment, day by day.
    - Web server logs
    - WAF logs
    - CDN logs
    - Load balancer logs
    - Web Apps logs
    - API gateway logs


## Windows Logs
With A SIEM WinEventLogs and Sysmon logs can be combined to provide clearer visibility for analysing activity.

### Sysmon logs
Used to observe a cariety of activity types such as malicious process execution, network connections, possible process injection, registry changes, file creation and more.

Examples: 

index=winenv EventCode=1 ** AND *EncodedCommand*
| table _time ComputerName ParentUser ParentImage ParentCommandLine Image CommandLine

A splunk query that detects launched processes (Event code 1) related to powershell that include the encodedcommand powershell arguments


index=winenv EventCode=3 ComputerName=WINHOST05
| table _time ComputerName Image SourceIp SourcePort DestinationIp DestinationPort Protocol

A splunk query that searches for network connections (event code 3) and filters by host

### WinEventLogs
Windows event logs contains over 200 different log channels, with the most commonly used being security, system and application logs.

Windows security logs:
The most commonly viewed and refrenced logs are the security logs. This is because security logs contains user authentication attemps, account creation or modification, access to files and registry keys, system restarts, log clearing and changes to audit or security policies.

Example splunk query:
index=winenv EventCode=4720 OR EventCode=4722
| table _time EventCode ComputerName Subject_Account_Name Target_Account_Name New_Account_Account_Name Keywords

Queries for new account creations for persistence

Windows System logs:
These logs record events generated by the operating system and its core services. These logs are a great place to look for potential persistence or privilege escalation attempts via services.

Example splunk query:
index=winenv EventCode=7045 OR EventCode=7036 ComputerName=WINHOST05
|  table _time EventCode ComputerName Service_Name Service_Account Service_File_Name Message

Query to ID anomalies with service creation and service start/stop events

## Linux Logs
When looking analysing Linux systems in a SIEM, there are two key log sources, auth.log which tracks authenticatin-related activity such as user logins and sudo usage which makes this log crucial for spotting failed logins, unauthorised access attempts or priviledge escalation. The other log is syslog, which captures general system-level events which allows monitoring of service restarts, cron jobs, and background processes which are all helpfull when building timelines or understanding  how the system behaves over time.

### Authentication Logs

- Unusual login activities: 
index=linux source="auth.log" *ubuntu* process=sshd 
| search "Accepted password" OR "Failed password"

- privilege escalation behaviours:
index=linux source="auth.log" *su*
| sort + _time

### System logs
- Persistence mechanisms:
index=linux sourcetype=syslog ("CRON" OR "cron") 
|  search ("python" OR "perl" OR "ruby" OR ".sh" OR "bash" OR "nc")

## Web application Logs
Every org has its own website and therefore a web server running it. Logs from these web servers are collected from Apache, Nginx and other resources. The most usefule for analysis are the access logs where requests to website resources can be detected. These logs can contain signs of malicious activity, such as scanning, DDoS attempts, various web-based attacks and web shell.

Example brute force activity query:
index=* method=POST uri_path="/wp-login."
| bin _time span=5m
| stats values(referer_domain) as referer_domain values(status) as status values(useragent) as UserAgent values(uri_path) as uri_path count by clientip _time
| where count > 25
| table referer_domain clientip UserAgent uri_path count status

Possible web shell activity query:
index=*
| search status=200 AND uri_path IN(*.php, *.phtm, *.asp, *.aspx, *.jsp, *.exe) AND (method=POST AND method=GET)
| stats values(status) as status values(useragent) as UserAgent values(method) as method
  values(uri) as uri values(clientip) as clientip count by referer_domain
| where count > 2
| table referer_domain count method status clientip UserAgent uri

DDoS Activity query:
index=* status=503
| bin _time =10m
| stats values(referer_domain) as referer_domain values(status) as status values(useragent) as UserAgent values(uri_path) as uri_path count by clientip _time
| where count > 100000
| table _time referer_domain clientip UserAgent uri_path count status
